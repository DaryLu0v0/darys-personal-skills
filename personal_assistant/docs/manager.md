# Research-library manager guide

Start by inspecting the actual local records, dashboard, update mechanisms and
source configuration. Read applicable repository instructions. Confirm canonical
paths and project-to-repository mappings before adding work. Existing evidence can
justify an update; an empty or ambiguous project needs a minimal initialization
plan and only the missing identity/evidence input. Never invent records or results.

Keep completed, active, possible, parked, closed and superseded paths. A checkpoint
explains **Goal / Done and learned / Next** with sources. Use meaningful research
decisions or outcomes, not one checkpoint per commit or chat message. Preserve
historical Next text, unsuccessful branches and multi-parent acyclic progression.
Collapse and filter choices belong to the view, not stored history.

Verify source URLs, branches and revisions. Distinguish this dashboard repository
from the repositories it catalogs. A folder name, worker claim or existing URL
does not establish a readable repository, confirmed identity or write permission.
Keep unavailable sources with explicit access limits; do not bypass restrictions.

Use selected native conversation/message references or approved handoffs. Separate
user decisions from assistant proposals, reported checks from inspected artifacts,
and software agreement from scientific validation. Record original work time when
known and evidence-check time separately. Do not claim complete history from
truncated pages or infer inactivity from missing inputs.

Each update has a stable ID, project ID, source revision, goal, completed scope,
findings, uncertainty, verification, next actions and evidence. Review the proposed
change, apply through digest/revision checks, validate the full graph and literature
references, replay to check idempotence, then verify the rendered dashboard.
Preserve immutable submissions, reconciliation decisions and all human edits.
Conflicts require a new reviewed reconciliation, not bypassing stale rejection.

Use one canonical Markdown note per paper and separate general summary from
project-specific relevance. Link a paper to all relevant contexts without copying
its editable content. Keep original PDFs, experiments and large datasets at their
established locations. Do not infer reading completion from metadata or an
attachment. Never attach an unverified bibliographic match.

The package's generated data is ignored by Git. Exporting or publishing personal
research, conversations, emails or notes needs separate destination and privacy
review. Keep source collection/scheduling permissions distinct from code installation.
Never silently install software, expand access, start experiments, publish or send
communications. Follow the owner's authorized scope and current app permissions.

Finish an update with **Changes made / Evidence checked / Needs attention / Next
action**, stating actual validation, commit/publication state and coverage limits.
